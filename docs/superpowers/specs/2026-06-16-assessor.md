# Assessor — Focused Milestone Spec (Plan 4)

> A focused milestone spec carved out of the locked v1 spec
> (`2026-06-15-adaptive-academy-redesign.md`, esp. §4.5 Assessor, §2.2 retention,
> §2.4 anchoring) and the evidence base
> (`docs/research/2026-06-15-learning-science-evidence.md`, §3 self-explanation,
> §8.4 illusion of competence, §8.2 over-reliance, §8.6 design implications). Same
> shape as Plans 2–3. New decisions / deviations from the v1 spec are in §2 for
> asynchronous objection.

## 0. Goal

Measure *real* understanding and feed it back into the adaptive loop. Given a generated
Topic — its `Concept`s (with `is_load_bearing` + `KnowledgeEstimate`), its `SourceDoc`s,
and a phase's "🎯 Ship" `Deliverable` — the **Assessor** runs **generative, anchored**
probes (never absolute scoring in a vacuum) that detect the **illusion of competence**:

- a **rubric-anchored self-explanation** probe ("explain *why* X works"),
- a **calibration check** (confidence prediction → probe → surface the gap), and
- an **artifact review** of the phase shippable against its acceptance-criteria rubric.

Each writes an `Assessment` recording **what it was graded against** (`rubric_id` /
`anchor_id` / prior baseline) and a **delta vs the user's own prior explanation**, then
**updates the `KnowledgeEstimate`** — which already drives `assistance_level` +
`challenge_level` (`engine/levels.py`), so assessment actually *moves the levers* and
surfaces specific gaps instead of being a report card. A **thin curated-retention
scaffold** proposes `SRSCard`s + `RecallPrompt`s for *load-bearing* concepts from
demonstrated gaps, which the user reviews before they enter SM-2 rotation.

## 1. Scope

### In scope
- `POST /api/concepts/{id}/assess` runs a probe (`kind ∈ self_explanation | calibration
  | artifact_review`; `source_quiz` is **deferred** — see §2.7) and persists an
  `Assessment` with `verdict`, `score`
  (0..1, **anchored**), `gaps[]`, `confidence_predicted/actual` (calibration),
  `rubric_id`/`anchor_id`/`baseline_assessment_id`, and `delta`.
- **Anchored grading.** A `Rubric` (prose `criteria`, deterministic `must_include`
  literal terms, `strong_signs`, `weak_signs`, source refs) is **generated on-demand and
  cached** per concept; source quizzes carry a `ReferenceAnchor` (question + reference
  answer + key points). Grading is LLM-as-judge **against the anchor**, combined with a
  **deterministic rules layer** so the grader can't be sycophantic (see §2.3).
- **Calibration collapses the IOED.** Elicit a confidence prediction, probe, then report
  predicted-vs-actual and the specific gap. Self-reported confidence is **never** used as
  the score (evidence §8.4).
- **The adaptive loop closes.** An `Assessment` updates the `KnowledgeEstimate` (level +
  confidence) via a pure `level_from_score`, reflected in the Tutor's next
  `assistance_level`/`challenge_level` — proven by an integration test (weak assessment →
  estimate drops → assistance rises).
- **Curated retention (thin).** Proposed `SRSCard`s + `RecallPrompt`s target load-bearing
  concepts, are **user-reviewed before rotation**, schedule via a pure SM-2 algorithm,
  and surface a "due now" queue; grading a due card runs SM-2 and can nudge the estimate.
- New data model (`Rubric`, `ReferenceAnchor`, `Assessment`, `SRSCard`, `RecallPrompt`) +
  Alembic migration; Plans 1–3 paths intact.
- Editable UI: run a probe → see verdict + score + gaps + anchor + delta + new estimate
  level; review/curate proposed retention cards and grade the due queue.
- Observable trace (one `AgentEvent` per step); generation tested with scripted clients;
  the rules layer, SM-2, `level_from_score`, and delta are pure & unit-tested.

### Out of scope (Plan 5+)
- **Automated delayed/surprise retention scheduling** (a background daemon) — v1 surfaces
  a due queue but does not run itself.
- **Assessor fan-out** variant generation (parallel probe/quiz/card generation across
  objectives) — reuses Plan 2's muscle; add later.
- **Full CurriculumDirector adapt-mode** re-sequencing on a flagged gap — a manual
  "remediate" trigger is enough for v1; automatic re-planning is deferred.
- Transfer/far-transfer item generation, build-in-public log, streaming, auth.
- Per-objective (sub-concept) rubrics — one `Rubric` per `Concept` for v1.

## 2. New decisions (deviations from the v1 spec — documented for objection)

### 2.1 Rubrics are generated on-demand and cached (not materialized by the CurriculumDirector)
The v1 spec has `Concept 1─1 Rubric` but is silent on *when* it's built. We generate the
`Rubric` **lazily** — on first assessment of a concept, from the `TopicFoundation` +
accepted `SourceDoc`s, in a single LLM call (mirroring `research.synthesize_foundation`),
then persist it (`reviewed_by_user=False`). Rationale: keeps Plan 3 untouched, avoids
generating rubrics for concepts never assessed, and matches the lazy pattern already in
the codebase. The user can review/edit a rubric before relying on it.

### 2.2 Single LLM call per probe, not fan-out
Each probe is **one structured `LLMClient.complete` call** (generate-or-grade), mirroring
Plans 2–3. Fan-out variant generation (many probes/cards in parallel) is deferred. Rubric
generation is also a single call.

### 2.3 Anchored score + a deterministic rules layer (anti-sycophancy)
Every `Assessment.score` is **anchored, never absolute**: the LLM grades the response
*against the rubric/anchor*, and a pure **rules layer** (`apply_rules_checks`) checks the
rubric's `must_include` literal terms against the response and the `weak_signs` for
misconceptions — contributing **hard gaps independent of the LLM**. The final score is the
LLM score **penalized** for each omitted required element (deterministic, floored at 0),
so a sycophantic "0.9" collapses when required elements are missing. This is the §2.4
"rules layer, not the LLM" requirement made concrete and is the load-bearing defense
against the very illusion-of-competence the Assessor exists to detect.

### 2.4 The estimate update is the point (assessment is adaptive, not a report card)
A pure `level_from_score(score) -> (level, confidence)` maps the anchored score to a
`KnowledgeEstimate` level (`>=0.75 → high`, `0.45–0.75 → medium`, `<0.45 → low`), written
back to the concept's estimate. Because `engine/levels.py` already derives
assistance/challenge from the estimate, a weak assessment **raises assistance** and lowers
challenge on the next Tutor turn. Closing this loop — not the probe itself — is the
milestone's reason to exist.

### 2.5 Calibration never trusts self-reported confidence
`assess` with `kind=calibration` records `confidence_predicted` (the user's pre-probe
self-rating, 0..1) and `confidence_actual` (the graded score), and reports the **gap**
(`confidence_predicted - confidence_actual`). The self-rating is logged for the
miscalibration signal **only** — it never contributes to the score (evidence §8.4: AI
learners feel more competent while learning less and are blind to it).

### 2.6 Retention is thin and curated
`SRSCard`/`RecallPrompt` are **proposed** (`status=proposed`) from demonstrated gaps for
**load-bearing** concepts, surfaced for the user to **activate/suspend** before rotation.
Scheduling is a pure SM-2 algorithm (`sm2_schedule`); the app exposes a **due-now queue**
(`GET /retention?due=true`, active items whose `due_at` has arrived) and a "grade a card"
path. No background daemon, no auto-injection — the evidence treats retention as a thin
scaffold relative to artifact work (§2.2).

### 2.7 `source_quiz` / `ReferenceAnchor` deferred to a later milestone
v1 ships the three evidence-spine probe kinds — **self_explanation, calibration,
artifact_review** — all rubric-anchored. `source_quiz` (graded against a per-source
`ReferenceAnchor`) is **deferred**: the `ReferenceAnchor` table exists for forward use,
but no `ensure_anchor` path is wired and the option is **not exposed in the UI** (the API
still accepts `kind=source_quiz` but grades it against the concept rubric — a degenerate
path not surfaced to the user). Wiring it later is a single lazy LLM call mirroring
`ensure_rubric` that sets `Assessment.anchor_id`.

### 2.8 Rules-layer strength depends on `must_include`
The deterministic anti-sycophancy penalty (§2.3) only bites when the generated `Rubric`
has non-empty `must_include` terms. The rubric prompt asks for 3–6 precise terms, and
rubrics are `reviewed_by_user`, but a lazy LLM rubric with empty `must_include` silently
degrades the defense to the raw LLM score. Known v1 limitation; a later pass can flag or
reject empty-`must_include` rubrics.

## 3. Architecture & module boundaries

Respects `models → engine → api`. The engine module mirrors `engine/curriculum.py` /
`engine/research.py` (pure helpers + orchestrators taking an injected `LLMClient`,
persisting, tracing via `AgentEvent`, returning a result dataclass).

```
POST /api/concepts/{id}/assess
  routes_assess.assess_concept_route
    └─ engine/assess.assess_concept(session, concept, kind, response, *, llm,
                                    confidence_predicted=None, baseline_id=None,
                                    item_id=None)
         ensure_rubric(session, concept, *, llm)        # get-or-generate-and-cache
         build_probe_grade_prompt(...)                  # pure: system + user
         llm.complete(...)                              # ONE structured call -> JSON
         parse_grade_json(text) -> GradeDraft           # pure
         apply_rules_checks(response, rubric)           # pure rules layer (§2.3)
         final_score = penalize(grade.score, rules_gaps)
         compute_delta(final_score, baseline?)          # pure
         → persist Assessment (anchor refs + delta + confidences)
         → level, conf = level_from_score(final_score); update KnowledgeEstimate
         → emit AgentEvent per step (topic-scoped)
         → AssessmentResult(assessment, estimate, events)

engine/retention.py  (pure SM-2 + thin orchestrators)
  sm2_schedule(ease, interval, reps, result) -> (ease, interval, reps)   # pure
  propose_retention(session, concept, assessment, *, llm) -> (cards, prompts)
  grade_card(session, card, result) -> SRSCard   # applies sm2_schedule + due_at
```

**Module responsibilities**
- `engine/assess.py` — rubric generation/caching, probe-grade prompt, JSON parse, rules
  layer, score penalty, `level_from_score`, `compute_delta`, the `assess_concept`
  orchestrator, result dataclasses.
- `engine/retention.py` — pure `sm2_schedule`, `propose_retention`, `grade_card`.
- `models.py` — `Rubric`, `ReferenceAnchor`, `Assessment`, `SRSCard`, `RecallPrompt`.
- `api/routes_assess.py` — assess + assessments-history + rubric routes;
  `api/routes_retention.py` — propose / list / review / grade / due.
- Frontend — a concept assessment panel + a retention review page.

## 4. Data model additions (SQLModel / SQLite)

```python
class Rubric(SQLModel, table=True):
    id: Optional[int] = primary_key
    concept_id: int = FK concept.id, unique         # one rubric per concept (v1)
    criteria: list[str] = JSON []                   # prose: what a correct explanation addresses (LLM)
    must_include: list[str] = JSON []               # literal terms the rules layer checks (§2.3)
    strong_signs: list[str] = JSON []
    weak_signs: list[str] = JSON []                 # misconceptions / red flags
    source_refs: list[str] = JSON []
    reviewed_by_user: bool = False
    created_at: datetime

class ReferenceAnchor(SQLModel, table=True):
    id: Optional[int] = primary_key
    source_doc_id: int = FK sourcedoc.id
    concept_id: Optional[int] = FK concept.id, nullable
    question: str
    reference_answer: str
    key_points: list[str] = JSON []
    created_at: datetime

class Assessment(SQLModel, table=True):
    id: Optional[int] = primary_key
    concept_id: int = FK concept.id
    item_id: Optional[int] = FK item.id, nullable           # if assessing a specific item/deliverable
    kind: str            # self_explanation | calibration | artifact_review | source_quiz | recall
    prompt: str
    response: str = ""
    verdict: str = ""
    score: float = 0.0                                      # 0..1, anchored (§2.3)
    gaps: list[str] = JSON []
    confidence_predicted: Optional[float] = None            # calibration (§2.5)
    confidence_actual: Optional[float] = None
    rubric_id: Optional[int] = FK rubric.id, nullable
    anchor_id: Optional[int] = FK referenceanchor.id, nullable
    baseline_assessment_id: Optional[int] = FK assessment.id, nullable   # self-FK
    delta: Optional[float] = None                           # score - baseline.score (§2.4)
    created_at: datetime

class SRSCard(SQLModel, table=True):
    id: Optional[int] = primary_key
    concept_id: int = FK concept.id
    front: str
    back: str
    source_ref: str = ""
    status: str = "proposed"     # proposed | active | suspended  (user curates)
    ease: float = 2.5            # SM-2 EF
    interval: int = 0            # days
    reps: int = 0
    due_at: datetime
    last_result: str = ""        # "" | again | hard | good | easy
    created_at: datetime

class RecallPrompt(SQLModel, table=True):
    id: Optional[int] = primary_key
    concept_id: int = FK concept.id
    prompt: str
    status: str = "proposed"     # proposed | active | suspended
    due_at: datetime
    last_result: str = ""
    created_at: datetime
```

JSON columns use `sa_column=Column(JSON)` (as `TopicFoundation`). The `Assessment`
self-FK (`baseline_assessment_id`) is a named FK; the table is created fresh (no batch
needed). **Migration** (`alembic revision`, down_revision `6cf13d007c01`): create the five
tables; `import sqlmodel`; round-trips upgrade/downgrade/upgrade on a clean DB **and**
after `just seed` (no batch alter this time, so no FK-recreation hazard). Plans 1–3 flows
intact.

## 5. API surface

| Method | Path | Body | Returns | Notes |
|---|---|---|---|---|
| POST | `/api/concepts/{id}/assess` | `{kind, response, confidence_predicted?, baseline_id?, item_id?}` | `AssessmentOut` | 404 concept; runs probe, persists, updates estimate; returns assessment + new estimate level |
| GET | `/api/concepts/{id}/assessments` | — | `list[AssessmentOut]` | newest first |
| GET | `/api/concepts/{id}/rubric` | — | `RubricOut` | get-or-generate-and-cache |
| POST | `/api/concepts/{id}/retention/propose` | `{from_assessment_id?}` | `RetentionOut` | proposes cards + prompts from gaps |
| GET | `/api/topics/{id}/retention` | `?status=&due=` | `RetentionOut` | list cards/prompts for the topic's concepts |
| POST | `/api/retention/cards/{id}/review` | `{status}` | `SRSCardOut` | activate / suspend (422 invalid) |
| POST | `/api/retention/cards/{id}/grade` | `{result}` | `SRSCardOut` | SM-2 update + new due_at (422 invalid) |

`AssessmentOut`: `{id, kind, prompt, response, verdict, score, gaps, confidence_predicted,
confidence_actual, delta, estimate_level}`. `RubricOut`: `{id, concept_id, criteria,
must_include, strong_signs, weak_signs, reviewed_by_user}`. `RetentionOut`: `{cards:
[SRSCardOut], prompts: [RecallPromptOut]}`. `ConceptOut` gains
`last_assessment_score: Optional[float] = None`.

## 6. Frontend surface

- **Concept assessment panel** (e.g. `/topics/[id]/assess` or a panel on the track page):
  pick a `Concept` + a probe `kind`; for calibration, enter a confidence (0–100%); type
  the explanation; submit → show `verdict`, `score`, `gaps[]`, the anchor it was graded
  against, the `delta` vs prior, and the **new estimate level** (assistance implication).
- **Retention review page** (`/topics/[id]/retention`): proposed cards/prompts with
  accept (activate) / suspend controls; a "due now" queue with grade buttons
  (again/hard/good/easy) that hit `/grade`.
- `lib/types.ts` + `lib/api.ts` gain `Assessment/Rubric/SRSCard/RecallPrompt/Retention`
  types and `assess/listAssessments/getRubric/proposeRetention/listRetention/reviewCard/
  gradeCard` clients (following the `j<T>` pattern); `lib/api.test.ts` covers the new
  clients.

## 7. Testing strategy

- **Pure / deterministic (no LLM, no network):**
  - `sm2_schedule` — again resets (reps 0, interval 1); good progresses (1 → 6 → ×ease);
    ease clamps at 1.3; hard lowers ease but still advances. Table-driven.
  - `level_from_score` — boundary cases at 0.45 / 0.75; returns level + confidence.
  - `compute_delta` — score − baseline; None baseline → None.
  - `apply_rules_checks` — omitted `must_include` term → a hard gap; present `weak_sign`
    → a misconception gap; clean response → no rules gaps.
  - score penalty — a high LLM score with N omitted required elements is floored correctly.
  - `parse_grade_json` / `parse_rubric_json` — parse well-formed JSON; strip ```json
    fences; defensive defaults (mirror `_parse_foundation_json`).
- **Orchestration (scripted clients):**
  - `ensure_rubric` — generates once (scripted), caches (second call: no LLM call).
  - `assess_concept` (self_explanation) — persists an anchored `Assessment`, applies rules
    gaps, updates the `KnowledgeEstimate`, emits one event per step, all topic-scoped.
  - `assess_concept` (calibration) — records predicted vs actual; score ignores the
    self-rating.
  - `propose_retention` — proposes cards/prompts (`status=proposed`) for the concept.
  - `grade_card` — applies SM-2 and advances `due_at`.
- **API:** assess happy path + 404; assessments history; rubric get-or-generate; retention
  propose/list/review/grade incl. the 422s.
- **Integration (the loop closes):** seed/generate a Topic → `POST /assess` with a weak
  explanation (scripted low score) → `KnowledgeEstimate` drops → `start_conversation` →
  `assistance_level` rises (low → high). Proves assessment moves the adaptive lever.
- **Regression:** existing 63 backend + 5 frontend tests stay green; migration round-trips
  clean **and** after seed; `just seed` + Plan 1–3 flows intact.

Live paths (real `AnthropicLLMClient` grading) stay thin and hand-verified, like Plans
1–3 (no real key in CI).

## 8. Risks

- **Grader sycophancy / illusion of competence** → mitigated by §2.3 (anchored score +
  deterministic rules-layer penalty); the whole agent exists to fight this, so the rules
  layer is load-bearing, not optional.
- **Score → level thresholds are guesses** → `level_from_score` thresholds are a single
  pure function, easy to tune; documented as empirical and unit-tested at the boundaries.
- **Self-FK migration / cascade** on `Assessment.baseline_assessment_id` → it's nullable
  and points within the same table; deleting concepts is out of scope here, so no cascade
  surprise (unlike Plan 3's import path).
- **Retention scope creep** → kept thin by §2.6 (proposals + SM-2 + due queue only);
  daemon/fan-out/adapt-mode explicitly deferred.
- **Calibration friction** (evidence §8.7 flags this) → calibration is one optional probe
  kind, not forced on every interaction.
